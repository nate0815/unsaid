# 文件回填（doc-sync）

把這次的變動同步回 `doc/` 四份文件。**先對規格，再回填** —— 順序不能反。

## 0. 最重要的一條

`doc/DESIGN.md` 是**唯一參照原則**。任何程式或其他文件與它牴觸，預設是**那邊錯了**，不是 DESIGN 過時了。

**你不得自行改寫 `doc/DESIGN.md` 來遷就實作。** 完整條款見 `doc/DESIGN.md` 開頭。

> 本檔是 Claude Code 與 Codex CLI **共用的正本**（放在工具中立的 `.agents/skills/` 下）。
> `.claude/skills/doc-sync/SKILL.md` 只是指回這裡的 stub，不要去改那份。

---

## 1. 先撈原料、再對規格（一定先做這步）

### 1a. 原料在 commit body，不在 diff

```bash
git -c core.quotepath=false status --short -uall
git -c core.quotepath=false diff
git log --format='%h%n%B%n---' <上次回填之後>..HEAD   # ⭐ 這行是「為什麼」的來源
```

**回填的「為什麼」一律先從 commit body 抄，不要從 diff 反推。**

diff 只講得出「改了什麼」。「為什麼這樣決定」在寫 commit 的當下還在腦子裡，
兩天後就得考古 —— 而考古一個兩天前的決策比當下記下來貴 5～10 倍，
還經常推不出來（於是 DEVLOG 就只剩流水帳，正是它最沒價值的形態）。

配套是寫 commit 時的規矩（見 §6）。**如果 commit body 是空的**，
別硬猜：直接問人「這個決定當初的理由是什麼」，比寫一個看似合理的錯理由好。

### 1b. 對規格

變動若已 commit 但沒回填，範圍取 `git log --oneline` 從最後一則 DEVLOG entry 之後。

拿變動內容逐項比對 `doc/DESIGN.md` 相關章節。

**有牴觸 → 停。照 §2 升報，等裁決。不要繼續往下做，也不要順手把 DESIGN 改成符合實作。**

沒牴觸 → 往 §3。

### 衝突分流

| 誰跟 DESIGN 不一致 | 怎麼處理 |
|---|---|
| **程式** | **停下來升報**，等裁決。不自行決定哪邊該改 |
| **PLAN／TECH／README** | 以 DESIGN 為準，直接改那幾份對齊 —— 不用問，但要在收工回報裡列出改了哪幾處 |
| **DESIGN 自己要改** | 一定要人點頭，且必須在版本紀錄寫「改了什麼＋為什麼」。機制怎麼擋你**依工具而異**：Claude Code 跳確認框（`permissions.ask`）；Codex CLI 直接擋下，要人建 `doc/.design-unlock` 才放行 —— **那個檔要由人建，你自己建等於自己授權自己**（hook 也會擋） |

## 2. 升報格式

發現程式與 DESIGN 牴觸時，輸出這張表加三個選項，然後**停下等回覆**：

```
⚠ 實作與規格不一致

| 項目 | doc/DESIGN.md 怎麼寫 | 實作變成怎樣 | 出處 |
|---|---|---|---|
| （名稱） | §X.Y （原文數值／敘述） | （現況） | src/xxx.js:NN |

要怎麼處理？
  1. DESIGN 是對的 → 我改程式回去符合規格
  2. 實作是對的 → 你授權我改 DESIGN（bump 版本、寫為什麼）
  3. 都先不動 → 進 DEVLOG 待決問題，標今天日期
```

出處要給到行號，讓人能直接點開看。

## 3. 路由表

> ⚠️ **移植時要改這張表**：TECH 的章節編號換成新專案的實際章號；
> 若新專案沒有拆 DEVLOG，把 `devlog/`／`decisions/`／`gotchas/` 三個落點改回
> `doc/DEVLOG.md` 的對應章節（同時要改 `.agents/hooks/doc-sync-check.mjs` 的 `GATE`）。
> ⚠️ 那支腳本 **Claude Code 與 Codex CLI 共用同一份**，改一次兩邊同時生效 ——
> 不需要、也不應該複製第二份出來。

| 這次改了什麼 | 回填到哪 |
|---|---|
| **規格／機制／結構／參數定義** | ⚠ **不自動改**。獲授權後才改 `doc/DESIGN.md` 對應章節（就地改成新版、**不留舊值在內文**）＋ §0 版本紀錄加一列 |
| 技術選型／架構決策／排程／風險／驗收 | `doc/PLAN.md` 對應章節 → §0 版本紀錄加一列 |
| 美術方針／尺寸規格／繪製規矩／製程與工具（**有 `doc/ART.md` 才適用**） | `doc/ART.md` 對應章節 → §0 版本紀錄加一列。⚠ ART **不是規格正本** —— 要把數字升級成規格得走上面 DESIGN 那一列，需授權 |
| **程式碼** | `doc/TECH.md` 的**收件匣章節**（最末節），一條一行加落點提示（`- （→ 模組契約）xxx`）。**不要當下決定該歸到哪一節** —— 那個判斷是回填最貴的部分，延後到實作穩定時一次做 |
| **新的不變式** | ⚠️ **例外，不進收件匣**：直接寫 `doc/TECH.md` 的不變式章節。那一節是動程式前的必讀，晚一天歸位就可能被違反 |
| 收件匣滿 10 條／實作穩定／要交付 | 整併：把收件匣條目**整段搬**進 §0 檔案清單／資料契約／模組契約／驗證章節，**不重新措辭**，搬完清空 |
| **任何一段工作（無例外）** | `doc/devlog/<今天>.md` —— 一天一檔，**新增或追加**：做了什麼／為什麼／卡在哪／下一步 |
| 有理由的決定 | `doc/decisions/<今天>-<標題>.md` **開新檔**；當天的 devlog entry 加一行連結 ＋ 一句話結論 |
| 推翻了先前決策 | 開新決策檔、`supersedes:` 指回舊那則；舊那則**只把 frontmatter 的 `status` 改成 `已推翻`，內文一個字都不動**；**不刪檔** |
| 待決問題有結論 | `doc/DEVLOG.md` §6 標日期與結論，**不刪掉**（這一節留在正本，因為要能一眼看完） |
| 踩到坑 | `doc/gotchas/<今天>-<症狀>.md` **開新檔**，寫「現象 → 原因 → 解法」三段，缺一不可 |
| 檔案結構／上手方式／驗證指令變了 | `README.md` —— **根目錄沒有 `README.md` 就先建一份**（見下節） |

### README 的必備章節

`README.md` 是**對外的進站點**，留在專案根目錄，不要塞進 `doc/`。

| 節 | 寫什麼 | 必備？ |
|---|---|---|
| `# <專案名>` ＋ 一句話 | 這是什麼、給誰 | ⭐ 必備 |
| `## 怎麼跑起來` | 可直接複製的最短指令 ＋「看到什麼算跑起來了」 | ⭐ 必備 |
| `## 文件在哪` | 指標表，指向 `doc/` 四份正本 ＋ `AGENTS.md` | ⭐ 必備 |
| `## 現在到哪了` | 成熟度、還不能做什麼 | 選用（prototype 建議留） |

**缺哪節就補哪節**，既有的內容不要為了對齊這張表而刪。

> ⚠️ **與 TECH「30 秒驗證」的分界**：README 寫的是**第一次怎麼把它跑起來**（給沒碰過這個專案的人）；
> TECH 那一節寫的是**怎麼確認它還沒壞**（給接手的人與你）。受眾與問題都不同，
> 所以兩邊都要有 —— 但**不要把同一段指令與判準抄成兩份**，那會分岔，而分岔不會報錯。

**深度內容不進 README**：檔案清單、資料契約、驗證判準、參數表一律留在 `doc/`，
README 只放連結。判準是**「這段內容過期了，誰會先發現？」** ——
答案是「改程式的人」就該寫在 `doc/TECH.md`。

### 動筆順序

0. **先撈 commit body**（§1a）—— 「為什麼」的來源
1. 先改正本（DESIGN 需授權／PLAN／TECH 收件匣／ART（有的話）／README）
2. **最後**才補 DEVLOG —— 順序反了會漏寫「為什麼」

## 4. 五條護欄

| 護欄 | 說明 |
|---|---|
| DESIGN 衝突一律升報 | 不自作主張選邊。這是本 skill 存在的主要理由 |
| 同一件事不寫在兩處 | 內容放對應正本，DEVLOG 只記「何時定案、為什麼」。發現重複要挑一處留 |
| DEVLOG 只追加不改寫 | 舊決策就算被推翻也**不刪檔**：開新決策檔用 `supersedes:` 指回去，舊那則**只改 frontmatter 的 `status`，內文不動** |
| DESIGN／PLAN 改完必 bump 版本 | 版本紀錄加一列，寫**改了什麼**與**為什麼改** |
| ⭐ **新寫的跨檔引用不寫章號** | 見下 |

### 跨檔引用寫章節標題，不寫章號

```
✅ TECH「不變式」          ✅ DESIGN「流程結構」
❌ TECH §16.7              ❌ DESIGN §10.8
```

**為什麼**：章號會因為在前面插一節就整批位移，而**沒有任何工具會報錯** ——
壞掉的引用會安靜地指到別的地方。標題改名的頻率遠低於章號位移，而且改名時搜得到。

**適用範圍**：從現在起**新寫**的引用。

- **既有的不回頭改** —— DEVLOG 是只追加不改寫的（改了就違反自己的護欄），
  TECH／PLAN 的量通常太大、一次改完的風險高於收益。讓它們隨自然改寫慢慢汰換。
- **同一份文件內部**的引用可以繼續用章號 —— 同檔內改章號時看得到全部出現處，
  風險低很多。這條規矩針對的是**跨檔**。

### 產出不是正本：Dataview／Bases 不能當資料來源

Dataview 與 Bases 是**執行時查詢**，`.md` 檔裡存的只有查詢語句，資料是 Obsidian
開啟那一頁時掃描 frontmatter 即時算出來的 —— **從來沒有被寫進檔案**。

你讀那一頁會得到**零筆資料**，而且不會有任何錯誤。這比讀不到更危險：
你會拿一個看起來很合理的錯答案繼續做。

**規矩**：frontmatter 是正本，Dataview／Bases 只是人看的視圖。
任何資料都不得只存在於查詢結果裡。要一覽就用上面那三行 `ls` 與 `grep`。

> **一條可以套用到所有形式的判準**：關掉 Obsidian、用記事本打開那個檔，
> **看不到的東西，你也看不到。**

其他：用**實際日期**（`date +%F` 取），不要寫「昨天」「上週」。

**判準寫「名字」不要寫「數量」**：`「這具名三張不穩定，其餘全部穩定」`
而不是 `「34 張裡 3 張不穩定、其餘 31 張穩定」`。後者每加一項就要回頭改好幾處數字，
沒改到也沒人發現。⚠️ 但不能只是刪數字 —— 要把判準改綁在**具名的例外**上。

**不必查編號、不必維護索引表**：檔名以日期開頭，就是 ID，永遠不會撞。要一覽時用查詢，不要讀整份：

```bash
ls doc/decisions/                              # 全部決策（日期＋標題都在檔名裡）
grep -L "status: 已推翻" doc/decisions/*.md    # 只列還生效的
grep -rl "<決策檔名>" doc/ src/                # 某決策影響了誰
```

## 5. 收工回報

回報一張表，不要只說「已更新文件」：

| 文件 | 章節 | 改了什麼 |
|---|---|---|
| doc/TECH.md | §3.2 | 新增 `xxx()` 的契約說明 |
| doc/devlog/2026-01-01.md | 新檔 | 追加當天 entry |
| doc/decisions/2026-01-01-xxx.md | 新檔 | 記錄「選了 A 不選 B」的理由 |

沒動到的文件也講一句為什麼沒動（例如「規格沒變，DESIGN／PLAN 不動」），讓人知道是判斷過的，不是漏掉。

## 6. commit 的時候要做的事（回填成本前移）

**這一節不是回填時執行的，是每次 `git commit` 時執行的。** 放在這裡是因為
它決定了 §1a 撈得到什麼 —— 回填貴不貴，在寫 commit 的當下就決定了。

### 規矩

**做了任何有「為什麼」的決定，commit body 就要有一行 `決策：X／因為 Y`。**

```
feat(<範圍>): <一句話標題>

決策：<選了 A，沒選 B>
因為：<B 的代價／A 的關鍵好處。寫得夠具體，讓三個月後的人不必重推一遍>
      <例：改走 B 的話，另外三個模組要跟著改介面，而 A 一行都不必動>

決策：<某個閾值／時機對齊「某個事件」，不是固定值>
因為：<固定值在某個情境下會出現什麼具體症狀>
⚠️ 這一項與指示有出入
```

> 重點在 `因為` 那幾行要**具體到能被反駁** ——「比較簡潔」「比較合理」等於沒寫。
> 寫得出「不這樣做會發生什麼」，三個月後才救得回來。

回填時 DEVLOG 的「決策」段就變成**搬運**，不是考古。

### 判斷要不要寫

| 情況 | 寫不寫 |
|---|---|
| 兩個做法選了一個 | **寫**，尤其要寫沒選的那個為什麼不選 |
| 與指示有出入 | **一定寫**，並標 ⚠️ —— 回填時要原樣帶進 DEVLOG 與收工回報 |
| 踩了坑才繞過去 | **寫**，寫「現象 → 原因」，解法 diff 自己看得出來 |
| 改一個 typo、換個變數名 | 不用 |

### 一條反向護欄

**commit body 不是 DEVLOG 的替代品，是它的原料。** 不要因為 body 寫得詳細
就跳過回填 —— body 散在 git log 裡、沒有結構、也不會被決策表收攏。
兩者的關係是「原料 → 成品」，不是「二選一」。
