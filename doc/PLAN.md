## 2. 技術方向結論

| 項目 | 選擇 | 一句話理由 |
|---|---|---|
| 部署 | 純前端，GitHub Pages（GitHub Actions 建置） | 沒有後端，個人訊息不離開瀏覽器 |
| 語言與建置 | TypeScript ＋ Vite | 三個模組共用同一份資料型別，不會各說各話；Pages 部署簡單 |
| 編輯器 UI | React ＋ React Flow（xyflow） | 流程圖的拖拉、連線、縮放不自己刻；React Flow 最成熟。見 [決策](decisions/2026-10-18-編輯器用-React-Flow-播放器零相依.md) |
| 播放器 | 原生 TypeScript，**零相依**，建成單一 JS | 要整份內嵌進匯出檔：要小、要多年後還打得開 |
| 字元繪製 | Canvas 2D ＋ 字形圖集，有效能需要再升 WebGL | 逐格特效與大量字元，DOM 文字做不到；和 ProjectHand 同一套思路 |
| 圖片轉字元 | 在編輯器端轉好，存「字元格 ＋ 參數」 | 匯出檔不必帶原圖，也不必帶轉換程式 |
| 匯出 | 播放器 JS ＋ 專案資料內嵌進 HTML 範本，用 `Blob` 下載 | 零伺服器。見 [決策](decisions/2026-10-18-純前端-匯出單一HTML.md) |
| 存檔 | IndexedDB 自動存 ＋ 匯入／匯出 `.json` | 關掉分頁不會掉進度 |

## 3. 核心判斷 ⭐

**播放器是獨立、零相依的小程式；編輯器預覽與匯出檔跑的是同一份播放器。**

- **為什麼**：H2 要求「匯出檔與預覽一致」。只要預覽用的是另一套程式（例如 React 元件），兩邊遲早分岔，而且分岔不會報錯。
  零相依則讓播放器小到可以整份內嵌。
- **如果錯了**（播放器長出對編輯器或框架的相依）：匯出檔變肥、需要網路載入、預覽與成品不一致 ——
  整條交付路線要重做。所以這條同時寫進 [AGENTS.md](../AGENTS.md)「這個專案的性質」。

## 4. 架構

```
src/
  core/     共用：專案資料型別、字元格、圖片轉字元、字形量測   ← 零相依
  player/   播放器：繪製、特效、流程推進、輸入                ← 只能用 core
  editor/   編輯器：React ＋ React Flow、Scene 面板、存檔、匯出  ← 可用 core、player
  spike/    M1 試作頁：拉桿調參數，原生 DOM                   ← 可用 core、player；M3 後移除
```

資料流向是單向的：`editor` 產生專案資料 → `player` 讀專案資料播放。
`core` 與 `player` 不能 import `editor`，這條規則讓「播放器能被單獨打包」成立。
實際檔案與介面寫在 [TECH.md](TECH.md)。

## 5. 必須做好的關鍵演出／關鍵路徑

| # | 是什麼 | 為什麼關鍵 | 做壞了會怎樣 |
|---|---|---|---|
| 1 | **訊息填充模式的畫面** | 這是 Unsaid 存在的理由（H1） | 只是另一個圖片轉 ASCII 工具，沒有理由做 |
| 2 | **匯出單一 HTML、手機上正常播放** | 交付方式本身（H2） | 做完了卻交不出去 |
| 3 | 中文全形字的排版 | 製作者與觀看者都以中文為主 | 句子錯位、斷字，訊息填充模式整個失效 |

## 6. 為什麼不用線上分享連結

| 面向 | 單一 HTML 匯出（本方案） | 線上分享連結（被否決方案） | 差在哪 |
|---|---|---|---|
| 後端 | 不需要 | 需要伺服器＋資料庫 | GitHub Pages 只能放靜態檔 |
| 隱私 | 訊息只存在製作者與觀看者手上 | 訊息存在第三方伺服器 | 個人訊息不上傳本身就是賣點 |
| 壽命 | 檔案在就能看 | 伺服器停了就全部失效 | 一封信應該能留很久 |
| 交付便利 | 要傳一個檔案 | 傳一條連結 | 連結比較方便 —— 這是本方案唯一的劣勢 |

## 7. 素材需求與版權

| 素材 | 來源 | 版權狀態 | 進版控？ |
|---|---|---|---|
| 製作者的圖片 | 製作者自備 | 製作者自負 | 否（只存在製作者的瀏覽器與匯出檔） |
| 開發測試用圖片 | Chiao 自備或自己拍 | 自有 | 少量、小檔可進 |
| 字型（若內嵌，見 DESIGN 待決 #3） | 開源等寬字型，候選：Noto Sans Mono CJK、Sarasa Gothic（更紗黑體） | 需為 OFL 等允許內嵌與再散布的授權 | 子集化後的檔案可進 |

**要不要開美術指南（`doc/ART.md`）**：不開 —— 沒有手繪或量產的視覺素材；畫面由製作者的內容與轉換演算法產生，
「好不好看」的驗證在 DESIGN 的 H1 與 M1 spike 裡做。若之後要做官方範本或範例訊息的視覺規範，再重新判斷。

## 8. 排程

沒有硬期限。每個里程碑結束都要有一個能給人看的東西。

| 里程碑 | 日期 | 內容 | 硬期限？ |
|---|---|---|---|
| **M0 地基** | 2026-10 | 文件系統、repo、Vite 骨架、GitHub Pages 自動部署 | 否 |
| **M1 視覺 spike** ⭐ | M0 後 | 一頁拉桿調參數：圖片轉字元（密度模式、訊息填充模式、中文全形）＋ 2～3 種特效。**回答 H1** | 否 |
| **M2 播放器 ＋ 匯出** | M1 通過後 | 手寫專案 JSON（3～4 個 Scene ＋ 1 個 Choice）、播放器、匯出單一 HTML、手機實測。**回答 H2** | 否 |
| **M3 流程編輯器** | M2 後 | React Flow 拖拉 node、連線、屬性面板、即時預覽、自動存檔 | 否 |
| **M4 Scene 編輯面板** | M3 後 | 換字元、調參數、加特效、轉場、逐格手修。**回答 H3** | 否 |
| **M5 打磨** | —— | 範本、範例訊息；第二階段功能（變數條件、文字輸入分支、音效）另行評估 | 否 |

**H1 不過就停在 M1**，不往下做編輯器。見 [決策](decisions/2026-10-18-先做視覺-spike-再做編輯器.md)。

## 9. 風險與應對

| 風險 | 機率 | 影響 | 應對 |
|---|---|---|---|
| 效果不夠打動人（H1 不成立） | 中 | 高 | M1 先做，不過就在 M1 調，不投入編輯器 |
| 對方裝置字型不同，畫面走樣（尤其中文） | 高 | 高 | M2 量測內嵌子集字型的檔案大小，交 Chiao 決定（DESIGN 待決 #3） |
| 低階手機上 Canvas 逐格特效掉幀 | 中 | 中 | M2 用手機實測；必要時降欄數、改 WebGL |
| 圖片或字型讓匯出檔過大 | 中 | 中 | 匯出只存字元格不存原圖；字型子集化 |
| 播放器不小心長出相依 | 低 | 高 | 寫進 AGENTS.md 與 TECH 不變式；`tests/boundaries.test.ts` 每次測試檢查 import；M2 起再加播放器 bundle 大小檢查 |

## 10. 驗收方式

- [ ] **H1**：Chiao 用自己的 2～3 張圖做出畫面，覺得「想拿給別人看」；給 1～2 人看，對方說得出畫面在講什麼或有明顯反應
- [ ] **H2**：關網路，電腦與手機各開一次匯出檔，走完所有分支，畫面與預覽目視一致；檔案 ≤ 5 MB（假值）
- [ ] **H3**：Chiao 從空白專案做完「5 個以上 Scene ＋ 1 個 Choice」的訊息，全程沒打開 JSON

## 11. 已排除的技術路線

| 路線 | 為什麼排除 | 什麼條件下會重新考慮 |
|---|---|---|
| Godot／Unity 網頁匯出 | 執行檔大、載入慢，不適合「一個小 HTML 檔」；編輯器 UI 也不如網頁好做 | 需要大量 3D 或物理效果時 |
| 後端＋分享連結 | 見本檔「為什麼不用線上分享連結」 | 交付便利性成為主要抱怨時 |
| DOM 文字（`<pre>`／`<span>`）繪製字元 | 逐格特效與數千個字元時效能差，也難做位移與透明度 | 需要讓觀看者選取、複製文字時，可加一層透明 DOM |
| Svelte ＋ Svelte Flow | 也可行；Chiao 選 React，React Flow 的生態與範例較多 | —— |
| 播放器也用 React | 匯出檔變肥，預覽與成品容易分岔（見「核心判斷」） | —— |
