# Unsaid — 開發日誌（DEVLOG）

> **這份文件是什麼**：本專案從需求到完成的**全過程紀錄**。
> **為什麼要寫**：專案的價值不只在做出來的東西，更在「當時為什麼這樣決定」。
> 未來要重做同一件事時，這份文件是省下重新踩坑的依據。
>
> **本檔是入口，不是全部。** 時序 entry、決策、踩坑各自**一則一檔**，
> 放在 `devlog/`、`decisions/`、`gotchas/`。本檔留的是規則、專案基本資料、
> 技術評估、待決問題 —— 那些不屬於任何單一則的東西。

## 0. 文件使用規則

> **本目錄四份文件的分工**：
> | 文件 | 職責 | 維護方式 |
> |---|---|---|
> | [DESIGN.md](DESIGN.md) | **做什麼** — 機制、規格、結構、參數 | 現在式；**⭐ 唯一參照，改動需授權** |
> | [PLAN.md](PLAN.md) | **怎麼做（方向）** — 技術選型、架構決策、排程、風險、驗收 | 現在式，就地改成最新版 |
> | [TECH.md](TECH.md) | **實際怎麼實作的** — 資料契約、模組契約、不變式、驗證方式 | 現在式，跟著程式改 |
> | DEVLOG.md（本檔 ＋ 三個資料夾） | **發生了什麼** — 進度、決策時點、踩坑 | 過去式，**只追加** |
>
> 規格變動 → 改 DESIGN（**需授權**）；做法方向變動 → 改 PLAN；**程式改了 → 改 TECH**；
> 全部都要在 `devlog/` 追加一則 entry。
> 同一件事不寫在兩處：DEVLOG 這一側只記「何時定案、為什麼」，內容本身放在對應的正本。

### 0.1 落點：哪種內容寫進哪個檔

| 內容 | 落點 | 檔名 |
|---|---|---|
| 一個工作段落發生了什麼 | `devlog/` | `YYYY-MM-DD.md`（一天一檔） |
| 一個有理由的決定 | `decisions/` | `YYYY-MM-DD-<一句話標題>.md` |
| 一個踩到的坑 | `gotchas/` | `YYYY-MM-DD-<症狀>.md` |
| 還沒有答案的問題 | 本檔 §6 | —— |
| 技術評估（含被否決的選項） | 本檔 §3 | —— |

**檔名就是 ID。** 日期開頭，所以永遠不會撞號 —— 不必查最大編號，也不必維護索引表。

> **為什麼拆檔**：時序 entry 佔體積最大、查詢率最低，決策與踩坑正好相反。
> 拆檔之後三件事一起解決：正本不會單向長大、決策編號不會撞、
> 而「這個決策影響了哪些 entry」由反向連結自動維護。
> **手工索引表會腐爛，`ls` 與 `grep` 不會。**

### 0.2 frontmatter — 這是查詢介面，不能省

三種檔各一組。欄位少寫沒關係，**寫錯欄位名會讓它從查詢結果裡消失**，比沒寫更糟。

```yaml
# decisions/YYYY-MM-DD-<標題>.md
---
type: decision
date: 2026-08-26
status: 生效                    # 生效 | 已推翻
supersedes:                     # 推翻了哪一則（檔名，不含 .md）
affects: [<模組>, <模組>]        # 影響哪些系統
code: [src/xxx.js]              # 對應到哪些程式檔
---
```

```yaml
# devlog/YYYY-MM-DD.md
---
type: devlog
date: 2026-08-26
day: 12                         # 跟著既有的走，不要按日曆重算
commits: [abc1234]              # 讓三個月後還撈得回 git show
decisions: [2026-08-26-<標題>]  # 這天定案的決策
---
```

```yaml
# gotchas/YYYY-MM-DD-<症狀>.md
---
type: gotcha
date: 2026-08-26
scope: <build | env | tooling | runtime>
---
```

### 0.3 查詢：取代索引表的四行指令

```bash
ls doc/decisions/                              # 全部決策一覽（日期＋標題都在檔名裡）
grep -L "status: 已推翻" doc/decisions/*.md    # 只列還生效的
grep -rl "<決策檔名>" doc/ src/                # 某決策影響了誰
grep -rln "type: gotcha" doc/gotchas/          # 全部踩坑
```

### 0.4 規則

| 規則 | 說明 |
|---|---|
| 只追加，不覆寫 | 舊 entry 就算後來被推翻也保留。推翻的做法是**新增一則決策**，把舊那則的 `status` 改成 `已推翻`、`supersedes` 指回去 —— 改 frontmatter 不動內文 |
| 一個工作段落一則 entry | 每則含：做了什麼／為什麼／卡在哪／下一步 |
| 決策一定寫理由 | 「做了什麼」誰都看得出來，「為什麼」三個月後就沒人記得 |
| **理由在 commit 當下就寫進 commit body** | 格式 `決策：X／因為 Y`。回填時決策檔是**抄**，不是從 diff 考古 —— 考古貴 5～10 倍而且常常推不出來 |
| **跨檔引用用相對路徑 Markdown 連結** | `[某決策](../decisions/2026-08-26-xxx.md)`，不用 `[[wikilink]]`（不帶路徑，AI 只能猜）。指向章節時寫**標題**不寫章號：`TECH「不變式」` 而非 `TECH §5` —— 章號位移沒有任何工具會報錯 |
| **entry 標題的 Day 編號跟著既有的走** | 不要自己按日曆重算 —— 中間可能有跳過的日子，重算會跟前一則對不上 |
| 技術評估結論要留否決選項 | 沒選的方案與否決原因，比選中的方案更有參考價值 |
| 待決問題不藏在內文 | 一律進 §6，解決後標記日期與結論，不要刪掉 |
| **Dataview／Bases 的產出不是正本** | 那是 render 時才算出來的，檔案裡只有查詢語句 —— AI 讀到的是零筆資料，而且不會報錯。frontmatter 才是正本 |

## 3. 技術評估

> **含被否決的選項與否決原因。** 只留選中的那個，這一節就白寫了。
> 落定成決策時，在 `decisions/` 開一則，本節那一列標明對應的檔名。

| 方案 | 評估結果 | 為什麼選／為什麼不選 | 對應決策 |
|---|---|---|---|
| 純前端 ＋ 單一 HTML 匯出 | ✅ 採用 | 不需後端、訊息不離開瀏覽器、檔案在就能看 | [純前端-匯出單一HTML](decisions/2026-10-18-純前端-匯出單一HTML.md) |
| 後端 ＋ 分享連結 | ❌ | 需要伺服器；GitHub Pages 只能放靜態檔；隱私與壽命較差 | 同上 |
| React ＋ React Flow 做編輯器 | ✅ 採用 | 流程圖套件最成熟，Chiao 選定 | [編輯器用-React-Flow-播放器零相依](decisions/2026-10-18-編輯器用-React-Flow-播放器零相依.md) |
| Svelte ＋ Svelte Flow | ❌ | 可行，但生態較小 | 同上 |
| Godot／Unity 網頁匯出 | ❌ | 執行檔大、載入慢，與「小 HTML 檔」衝突 | —— |
| Canvas 2D 繪製字元 | ✅ 採用 | 逐格特效、大量字元；DOM 文字做不到 | —— |
| 字形層 ＋ `source-in` 一次上色 | ✅ 採用 | 200 欄×88 列、3000 字、波浪＋故障全開，每幀約 6 ms | [Canvas繪製-逐格放字-字形層一次上色](decisions/2026-10-18-Canvas繪製-逐格放字-字形層一次上色.md) |
| 逐格設 `fillStyle` ＋ `fillText` | ❌ | 原圖色模式每格一次狀態切換，數千格預期會掉幀（**未實測**，是推估） | 同上 |
| gifuct-js（解碼）＋ gifenc（編碼） | ✅ 採用 | 小、MIT、純 JS；疊合規則自己寫成純函式並測過 | [GIF讀寫用gifuct-js與gifenc-放在media](decisions/2026-10-18-GIF讀寫用gifuct-js與gifenc-放在media.md) |
| 瀏覽器內建 `ImageDecoder` 讀 GIF | ❌ | 不是每個目標瀏覽器都支援（DESIGN 要支援近兩年的 Safari、Firefox），要有後備就變兩條路 | 同上 |
| 自己寫 GIF 編解碼器 | ❌ | LZW、調色盤量化都有現成且測過的實作，自己寫只多出錯機會 | 同上 |
| 字元格高寬比由字型量測 | ❌ | 各裝置字型不同 → 圖在對方那邊變形 | [字元格高寬比固定為2](decisions/2026-10-18-字元格高寬比固定為2.md) |

## 4. 開發日誌 → `devlog/`

**時序 entry 一天一檔**，檔名 `devlog/YYYY-MM-DD.md`。本節只留寫法，不留內容。

```markdown
---
type: devlog
date: 2026-08-26
day: 12
commits: [abc1234]
decisions: [2026-08-26-<標題>]
---

# 2026-08-26（週三）— Day 12：<一句話標題>

**做了什麼**
-

**決策**
- [<決策標題>](../decisions/2026-08-26-<標題>.md) —— 一句話結論，理由在該檔

**卡在哪／踩到什麼**
- [<症狀>](../gotchas/2026-08-26-<症狀>.md)

**下一步**
-
```

> **決策與踩坑在這裡只放連結與一句話結論**，內容本身在對應的檔。
> 這樣反向連結面板才會在決策檔那側列出「哪些 entry 提到我」。

## 5. 決策記錄 → `decisions/`

**一決策一檔**，檔名 `decisions/YYYY-MM-DD-<一句話標題>.md`。

```markdown
---
type: decision
date: 2026-08-26
status: 生效
supersedes:
affects: []
code: []
---

# <決策標題>

**選了什麼**
-

**沒選什麼、為什麼不選**
-

**如果錯了會怎樣**
-
```

**推翻舊決策的做法**（三步，缺一不可）：

1. 新開一則決策檔，`supersedes:` 填舊那則的檔名
2. 舊那則的 frontmatter 把 `status:` 改成 `已推翻` —— **只改 frontmatter，內文一個字都不動**
3. 在當天的 `devlog/` entry 記一筆，連到兩則

> 被推翻的決策**不刪檔**。它記錄了「這條路試過，不行」—— 那是全套文件裡
> 唯一無法從 `git log` 重建的東西。

## 7. 踩坑筆記 → `gotchas/`

**一坑一檔**，檔名 `gotchas/YYYY-MM-DD-<症狀>.md`。

```markdown
---
type: gotcha
date: 2026-08-26
scope: build
---

# <症狀，用看得到的現象命名>

**現象**
-

**原因**
-

**解法**
-
```

> 只寫現象或只寫解法都會讓下一個人重新查一遍。**三段都要有。**
> 症狀當檔名，因為下次遇到時你記得的是症狀，不是原因。
